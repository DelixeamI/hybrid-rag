# DESIGN.md — журнал решений

Формат записи: **Проблема / Решение / Отвергнутая альтернатива / Цена** (латентность, деньги, сложность).
Числа в записях взяты из `reports/results.md` (фикстура, прогон 2026-10-19). Они описывают синтетический корпус из 20 статей, а не настоящий ТК РФ, и меняются при каждом новом `make eval`.

---

## D1. Тесты и eval без сети и ключей: интерфейс LLM и кассеты

**Проблема.** Тесты и eval, зависящие от живой LLM, недетерминированы, стоят денег и не запускаются на CI.

**Решение.** LLM спрятана за `LLMClient` с тремя реализациями: `FakeLLM` (юнит-тесты), `RecordedLLM` (кассеты в `tests/cassettes/`, имя файла = sha256 от модели, системного и пользовательского промпта), `OpenAICompatibleLLM` (реальный вызов; Ollama, Gemini или облако через `base_url`). `make record` прогоняет eval на реальной модели через `RecordingLLM` и перезаписывает кассеты. По умолчанию `LLM_MODE=recorded`, чтобы случайный запуск не ушёл в сеть. При отсутствии кассеты `RecordedLLM` падает с понятным сообщением, а не подставляет ответ.

**Отвергнутая альтернатива.** Моки через `unittest.mock`: не проверяют формат реального ответа модели, eval на моках ничего не измеряет.

**Цена.** Любое изменение промпта, модели или состава контекста инвалидирует кассеты, нужен `make record` (реальные запросы, у бесплатного Gemini есть лимиты). Кассеты зависят от порядка и состава top-5 чанков, то есть от скоров reranker: на другом железе численный шум теоретически может переставить почти равные чанки и дать cassette miss. Тогда CI падает громко, а не молча. Проверено на одной машине: фикстурный `eval` с кассет проходит одинаково при ранжировании на GPU и только на CPU (`CUDA_VISIBLE_DEVICES=-1`); Linux-CI с CPU-сборкой torch ещё не запускался.

## D2. Фикстура синтетическая; отчёты по датасетам раздельные

**Проблема.** Настоящий текст кодекса мог быть недоступен при разработке, а ждать его нельзя: конвейер и тесты должны работать сразу. Если выдать вырезки «по памяти» за официальный текст, это ложь.

**Решение.** `tests/fixtures/tk_fixture.txt` — вручную написанные приближения 20 статей с пометкой SYNTHETIC в начале файла и в отчёте. Датасет выбирается флагом `--dataset fixture|full`; `full` берёт `data/raw/` и `data/golden.jsonl`, отчёт пишется отдельно (`results_full.*`). Отчёт по фикстуре всегда содержит предупреждение.

**Отвергнутая альтернатива.** Положить в `tests/fixtures/` реальные фрагменты кодекса без проверки: легко внести тихую ошибку в юридический текст.

**Цена.** Метрики на фикстуре почти ничего не говорят о качестве на кодексе: корпус мал, один вопрос двигает метрику на несколько процентов, пороги CI-гейта привязаны к этому набору.

## D3. Чанк = статья целиком

**Проблема.** Нужна единица поиска, по которой можно дать ссылку «статья N, часть M».

**Решение.** Статья короче ~500 токенов (токенайзер e5) идёт одним чанком. Длинные режутся окнами по частям с перекрытием в одну часть; слишком длинную часть режем по предложениям. В каждом чанке breadcrumbs «ТК РФ > Глава > Статья N. Название», номер статьи и номера частей. Эмбеддится и показывается LLM текст вместе с breadcrumbs. Утратившие силу статьи не индексируются.

**Отвергнутая альтернатива.** Чанки фиксированного размера по символам или токенам: рвут норму посередине, ломают ссылки на часть, цитата может оказаться в двух чанках.

**Цена.** Статья целиком — шумный вектор для e5 (одна мысль в одной части теряется среди других), и контекст LLM длиннее. Оценить, насколько это вредит на настоящем кодексе, нельзя без `data/raw/`.

## D4. Sparse-канал: BM25 поверх лексем Postgres, а не `ts_rank_cd`

**Проблема.** Нужна sparse-часть без внешних сервисов. Первая версия брала `ts_rank_cd` (ранжирование Postgres FTS). Оно не использует IDF: частые слова («отпуск», «работник») весят как редкие. В отчётах это выглядело как слабый sparse-канал, из-за которого гибрид был хуже dense.

**Решение.** Postgres делает языковую работу: конфигурация `russian` (стемминг, стоп-слова), лексемы из `to_tsvector`. Ранжирует собственный BM25 (k1=1.2, b=0.75, IDF по Робертсону и Спарк Джонс) в памяти приложения, индекс строится при старте из таблицы `chunks` (`src/tkrag/retrieval/bm25.py`). Запрос по-прежнему ИЛИ по словам вопроса. Прежний вариант оставлен режимом `fts`, чтобы разница была видна в таблице отчёта. GIN-индекс по `tsvector` остаётся: он нужен режиму `fts`.

**Отвергнутая альтернатива.** `pg_search`/ParadeDB или Elasticsearch: честный BM25 внутри хранилища, но это новое расширение или сервис. `plainto_tsquery` (И по словам) почти ничего не находит на разговорных вопросах. Другие варианты ранжирования FTS (`ts_rank`, нормализация по длине, поиск только по заголовкам) мы замерили: они лучше `ts_rank_cd`, но хуже BM25 (`reports/experiment_hybrid.md`).

**Цена.** Индекс лежит в памяти процесса и строится при старте: для одного кодекса (сотни чанков) это секунды и килобайты, для миллионов чанков не годится (там нужен `pg_search` или внешний поиск). Новая редакция в БД не видна запущенному API до перезапуска. BM25 считается в Python, а не в SQL.

## D5. RRF с весом dense, параметры подобраны на отдельной половине вопросов

**Проблема.** Скоры dense (косинус) и sparse (BM25) несравнимы по шкале; на первой версии гибрид с равными весами и `ts_rank_cd` был сильно хуже dense.

**Решение.** Reciprocal Rank Fusion с весами: `score = Σ w / (k + rank)`. `k` и вес dense вынесены в конфиг (`RRF_K`, `RRF_DENSE_WEIGHT`). По 50 кандидатов с каждой стороны. Параметры выбраны экспериментом `scripts/experiment_hybrid.py`: вопросы с ответом делятся поровну на DEV и TEST (по типам, фиксированный seed), 36 конфигураций (6 sparse-каналов, k из {10, 60}, вес dense из {1, 2, 3}) сравниваются на DEV, победитель по правилу «лучший MRR, затем Recall@5, затем ближе к прежним настройкам» проверяется на TEST. Победитель: BM25, k=10, вес dense 3. Это значения по умолчанию, они отличаются от классических k=60 и равных весов; классическая настройка включается переменными окружения.

**Что показал эксперимент** (`reports/experiment_hybrid.md`, на TEST):
- замена `ts_rank_cd` на BM25 чинит гибрид: прежний гибрид сильно хуже dense, гибрид с BM25 не хуже;
- победитель DEV немного лучше dense и на TEST по Recall@1, Recall@5 и MRR, но разница в один-два вопроса из 37, то есть в пределах шума. Уверенно утверждать «гибрид лучше dense» эти данные не позволяют;
- в таблице по всему golden (`reports/results_full.md`) параметры подобраны на половине этих же вопросов, поэтому эти числа оптимистичнее честной оценки.

**Отвергнутая альтернатива.** Взвешенная сумма нормализованных скоров: нужна нормализация шкал, на малом golden легко переобучить. Подбор параметров на всём golden: тогда нет честной проверки.

**Цена.** Лишние параметры (вес, k) и риск переобучения на 76 вопросах. Эксперимент надо повторить на большем golden. Веса зависят от пары «e5-small + BM25»: смена модели эмбеддингов требует нового прогона.

## D6. Reranker поверх гибрида

**Проблема.** Первый этап приблизителен; нужна точная пересортировка и калиброванный скор для отказа.

**Решение.** Top-20 из гибрида → cross-encoder `BAAI/bge-reranker-v2-m3` → top-5; выход через сигмоиду в [0, 1]. В тестах — детерминированный `LexicalReranker`, чтобы CI не качал 2,2 ГБ.

**Отвергнутая альтернатива.** Без reranker: быстро, но скор hybrid (RRF) нельзя использовать как порог отказа: он зависит только от рангов, лучший документ всегда получает ~одинаковый скор.

**Цена.** Латентность. Первый замер был на CPU (по ошибке установки `torch+cpu`): p50 около 6,5 секунды на запрос на фикстуре и около 22 секунд на настоящем корпусе (чанки в среднем 275 токенов, 20 кандидатов). На RTX 5070 (`torch+cu130`) p50 около 0,5 секунды на настоящем корпусе, то есть в десятки раз быстрее остальных режимов, но всё ещё на порядок медленнее dense. Без GPU нужна модель поменьше или меньше кандидатов. Качество: на настоящем корпусе (черновой golden) hybrid+rerank лучший, особенно на перифразах (Recall@1 72,7% против 45,5% у dense), так что выигрыш реальный; платить за него приходится латентностью и необходимостью GPU. Числа рядом с этой записью (72,7% и 45,5%) взяты из отчёта на момент написания.

## D7. Порог отказа по скору reranker, подбор на DEV и проверка на TEST

**Проблема.** Для вопросов вне кодекса (налоги, ипотека) модель склонна выдумывать ответ из ближайших статей. Порог отказа нужно где-то взять, и если подобрать его на тех же вопросах, на которых потом считается «доля верных отказов», цифра будет завышена.

**Решение.** Если лучший скор reranker ниже порога, отвечаем отказом и не вызываем LLM (экономия денег и времени). Вторая линия: модель сама может вернуть `refused=true`. Порог выбирается как максимум «верные отказы минус ложные отказы» **только на DEV-половине** golden (все 92 вопроса делятся стратифицированно пополам фиксированным seed, `split_dev_test`; половина вопросов с ответом совпадает с той, на которой подбирались параметры гибрида). Метрики отказов в отчёте выводятся тремя колонками: всё, DEV (здесь порог подобран) и TEST (отложенные вопросы), с размерами выборок в виде `k/n`. Порог хранится в датасете (`tkrag.datasets`), потому что скоры зависят от корпуса: 0,003 для синтетической фикстуры, 0,0069 для кодекса. Переменная `REFUSAL_THRESHOLD` переопределяет оба.

**Отвергнутая альтернатива.** Порог по RRF: скор зависит только от рангов, а не от близости к вопросу. Порог по косинусу dense мы не пробовали, это возможная проверка. Подбор порога на всём golden (так было сначала: 0,0066): проще, но метрика отказов измеряется на тех же вопросах и завышена.

**Что показал TEST** (`reports/results_full.md`, колонка TEST): все вопросы без ответа в TEST отказаны, ложных отказов на вопросах с ответом нет. Это проверка на отложенных вопросах, но слабая:
- в TEST всего 8 вопросов без ответа и 37 с ответом, один вопрос меняет метрику на 12 и 3 пункта соответственно;
- вопросы `no_answer` в golden лёгкие (налоги, паспорта, штрафы ГИБДД), далёкие от трудового права; почти нет пограничных вопросов (например, «об отпуске по гражданско-правовому договору», «о пособии, которое платит не работодатель»), так что реальное качество отказов на трудных случаях неизвестно;
- запас по скору небольшой: на TEST у вопросов без ответа максимум около 0,005, у вопросов с ответом минимум около 0,008, а порог 0,0069 лежит между ними; один трудный перифраз с чуть более низким скором уже даст ложный отказ.

**Цена.** Половина данных не участвует в подборе, поэтому порог выбран по меньшей выборке (47 вопросов, из них 8 без ответа) и чувствителен к ней. Независимую оценку даст только новый набор по другим статьям (`--frozen`, README и PROGRESS), и такого набора пока нет.

## D8. Детерминированный пост-валидатор (grounding) и деградация

**Проблема.** Даже при инструкции «только по контексту» модель может исказить число («28» → «30») или сослаться на несуществующую статью. Для юридического текста это хуже отказа.

**Решение.** После генерации без участия модели проверяем: цитаты являются настоящими фрагментами чанков (без учёта регистра, ё и пунктуации; многоточие может пропускать слова). Если модель пересказала цитату, но по смыслу она близка к реальному фрагменту (Jaccard по значимым словам не меньше 0,6), показывается **реальный** фрагмент, а не пересказ; если не похоже ни на что, ответ отклоняется; в ответе есть ссылки `[n]`, ведущие на процитированные фрагменты; каждое число с единицей (дней, часов, недель, месяцев, лет, %, рублей; цифрами и словами) есть в процитированных чанках, причём «две недели» и «14 дней» считаются одним и тем же; каждый номер статьи — среди процитированных или упомянутый внутри них. Не прошло → статус `unverified`, текст ответа **заменяется** списком релевантных статей с цитатами. Невалидный JSON от модели обрабатывается так же.

**Что это не гарантирует.** Валидатор проверяет *grounding* (опору на цитируемый текст), а не *смысловую корректность*. Ответ, прошедший проверку, содержит только числа и номера статей из процитированных фрагментов, но может выбрать не ту норму или сделать неверный вывод. Поэтому «доля подтверждённых ответов» в отчётах означает долю прошедших проверку среди данных ответов, а не долю юридически верных. Смысловую корректность частично измеряет `answer_facts` recall (лексически), полностью её может измерить только ручная или экспертная оценка.

**Отвергнутая альтернатива.** Вторая LLM как судья: недетерминированно, стоит денег, сама ошибается; её можно добавить как опцию поверх, не вместо.

**Цена.** Числа без единиц, даты и смысл утверждения не проверяются (ответ может цитировать верную статью и делать из неё неверный вывод). Остаются ложные срабатывания: например, «30 дней» против «месяц» не сопоставляются (месяцы разной длины), а число из другого, неподписанного фрагмента контекста отклоняется, даже если оно там есть: модель должна сослаться именно на тот фрагмент. Починка цитат на повторном просмотре 77 записанных ответов (кассеты предыдущего прогона, офлайн, без модели) вернула 5 из 10 отклонённых; оставшиеся 5 это 2 числа не из процитированных фрагментов (проверка сработала верно), 2 цитаты, ни на что не похожие, и 1 ответ без ссылок. Для `answer_facts` recall считается только по принятым ответам (`ok`): деградированный ответ считается нулём.

## D9. Отпечаток индекса и пересборка при смене настроек

**Проблема.** Ингест пропускался, если sha256 исходного файла совпадал. Но индекс зависит не только от файла: сменили модель эмбеддингов, размер чанка или алгоритм разбора, и в БД остаются старые векторы и чанки. В худшем случае поиск тихо ухудшается, а при другой размерности вставка падает. Работающий API при этом продолжал бы ранжировать BM25-индексом, построенным при старте, хотя чанки в БД уже заменены.

**Решение.** В таблице `documents` хранится `index_fingerprint` = sha256 от: sha256 файла, имени модели эмбеддингов, размерности, лимита токенов чанка, `PARSER_VERSION` и `CHUNKER_VERSION` (`src/tkrag/ingest/fingerprint.py`). Ингест пропускается только при совпадении отпечатка; иначе документ пересобирается одной транзакцией, а отчёт пишет «rebuilt». Старые строки без отпечатка пересобираются один раз. Размерность проверяется заранее: при несовпадении с колонкой `vector(N)` ингест падает с понятным сообщением, что нужна миграция. BM25-индекс в API обёрнут в `Bm25Cache`: на каждый запрос одна дешёвая проверка идентификатора последней версии документа, при изменении индекс перестраивается.

**Отвергнутая альтернатива.** Сравнивать только sha256 файла (как было): просто, но молча оставляет неверный индекс. Пересобирать всегда: надёжно, но каждый запуск стоит минуты эмбеддингов.

**Цена.** Версии парсера и чанкера нужно поднимать руками, когда меняется их логика: забытое увеличение оставит устаревший индекс (тесты фиксируют входы отпечатка, но логику не видят). Проверка версии добавляет один запрос к БД на каждый вопрос в API. Смена размерности по-прежнему требует ручной миграции.

## D10. Метрики поиска для вопросов с несколькими статьями

**Проблема.** Правило «найдена хотя бы одна ожидаемая статья» верно, когда статьи перечислены как альтернативы (на вопрос отвечает любая), но неверно для `multi_article`: ответ на вопрос про статьи 115 и 125 по одной 115 неполон, а метрика засчитывала его целиком.

**Решение.** Определение зависит от типа вопроса (`GoldenItem.needs_all_articles`). Для `multi_article` Recall@k равен доле найденных обязательных статей, а MRR считается по рангу последней из них (ноль, если какой-то нет). Для остальных типов остаётся «любая из ожидаемых». Отчёт содержит раздел «Misses» с вопросами, найденными не полностью, и пояснение определения.

**Отвергнутая альтернатива.** Один общий строгий критерий «все статьи» для всех типов: у вопросов с альтернативами он занижал бы результат. Оставить прежнее: завышает результат ровно там, где вопрос сложнее всего.

**Цена.** Числа до и после изменения несравнимы на вопросах `multi_article` (их в golden 10 из 92). Прежние отчёты и результаты эксперимента `reports/experiment_hybrid.*` пересчитаны с новой метрикой.
